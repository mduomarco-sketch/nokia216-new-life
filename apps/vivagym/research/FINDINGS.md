# VivaGym / MyVitale check-in QR — reverse-engineering notes

**Goal:** let a registered member display their *own* gym check-in QR on a
non-smartphone (KaiOS / BlackBerry) without the full Android app.

**Source material:**
- `the VivaGym Android app (v2.0.13 XAPK)` (base APK `com.myvitale.vivagym.group`, native Java/Kotlin, 10 DEX)
- Two screenshots of my own check-in QR (not published)

---

## 1. What the QR actually contains

Both screenshots decoded to:

```
exerp:checkin:123p456789-1700000000000-0123456789abcdef0123456789abcdef
exerp:checkin:123p456789-1699999914295-fedcba9876543210fedcba9876543210
```

Structure:

```
exerp : checkin : <memberId> - <timestampMillis> - <32-hex digest>
         scheme    123p456789   1700000000000      01234567...abcdef
```

| Field          | Value in sample 1            | Notes |
|----------------|------------------------------|-------|
| scheme/action  | `exerp:checkin`              | Exerp is the gym-management platform behind VivaGym |
| memberId       | `123p456789`                 | **constant** across both codes — identifies the member |
| timestamp (ms) | `1700000000000`              | <timestamp>; sample 2 is ~86 s earlier → **token rolls over time** |
| digest         | `0123...abcdef` (32 hex / 128-bit) | MD5-length HMAC/hash, **computed server-side** |

The turnstile scanner reads this string and validates the digest against the
Exerp backend.

---

## 2. Where the QR comes from — the key finding

**The app does NOT build the QR string or compute the hash locally.**
It asks the server for the finished string and just renders it with zxing.

From `com/myvitale/api/Api.java`:

```java
@GET("api/v2.0/exerp/qr")
Call<String> getQR();          // server returns the full "exerp:checkin:..." string
```

Consequences:
- **There is no client-side secret to extract** — nothing in the APK signs the token.
- The timestamp and the 32-hex digest are **generated by `vivagym.myvitale.com`** on each call.
- So the entire "auth engine" a dumbphone needs is: *authenticate → GET the QR string → render it.* No crypto on device.

This is the ideal shape for a KaiOS/BlackBerry port: it's just an authenticated
HTTPS GET plus any QR-rendering library.

## 3. Authentication flow (verified in `ApiService` + `AuthInterceptor`)

**Base URL:** `https://vivagym.myvitale.com/`
(`NetworkModuleKt.SERVICE_URL`, also legacy `BuildConfig.URL_DOMAIN`)

**App name constant:** `vivagym` (`NetworkModule.provideAppName()`)

Login is **two steps**: an app-level OAuth2 client-credentials grant, then the
user login that consumes the resulting "temp token".

### 3.1a Step 1 — app client-credentials -> temp token
Symfony FOSOAuthServerBundle (`oauth/v2/token`). The app POSTs a JSON body;
GET query params or POST form also work.
```
POST oauth/v2/token
{ "grant_type":"client_credentials", "client_id":"<id>", "client_secret":"<secret>" }
→ LoginResponse { access_token: <TEMP_TOKEN>, ... }
```
Client credentials are hardcoded in the APK (this is the *app* identity, not a
user secret). Two pairs ship; the live login path (`ApiHelperImpl.authenticate`)
uses the `BuildConfig` pair:
```
# BuildConfig (used by the live login flow)
CLIENT_ID     = <CLIENT_ID from BuildConfig>
CLIENT_SECRET = <CLIENT_SECRET from BuildConfig>
# Authentication storage (alternate / fallback)
CLIENT_ID     = <alternate CLIENT_ID>
CLIENT_SECRET = <alternate CLIENT_SECRET>
```

### 3.1b Step 2 — user login (consumes the temp token)
```
POST api/v2.0/{locale}/exerp/newAuth          (locale e.g. "es")
Content-Type: application/x-www-form-urlencoded

access_token=<TEMP_TOKEN from step 1>    # NOT empty — this is why a bare login 400s
password=<your password>
email=<your email>
appName=vivagym
```
Mapping confirmed in `ApiHelperImpl.login()`:
`apiService.login(locale, access_token=tempToken, password, email, appName)`.

Response (`LoginResponse`, standard OAuth2 shape):
```json
{
  "access_token":  "....",
  "refresh_token": "....",
  "token_type":    "Bearer",
  "expires_in":    3600,
  "code":          0,
  "message":       "..."
}
```

### 3.2 Authenticated calls — attach the token
Every `/api/...` request (except `forgot`, `refresh`, `app/info`, `newAuth`) gets:
```
Authorization: Bearer <access_token>
```
(`TOKEN_FORMAT = "Bearer %s"` in both `ApiService` and `AuthInterceptor`.)

### 3.3 Token refresh
```
GET api/email/refresh?refresh_token=<refresh_token>   → new LoginResponse
```
On 400/401/404/500 the app wipes tokens and forces re-login.

### 3.4 Get the QR
```
GET api/v2.0/exerp/qr
Authorization: Bearer <access_token>
→ body: the string  exerp:checkin:123p456789-<ts>-<hash>
```
(Returned via Retrofit `Call<String>` with the Gson converter, so the body is
typically a JSON-quoted string — strip surrounding quotes if present.)

## 4. Minimal client logic (what the KaiOS app must do)

```
0. POST oauth/v2/token (client_credentials, client_id, client_secret) → TEMP_TOKEN
1. POST newAuth  (access_token=TEMP_TOKEN, email, password, appName=vivagym) → user access_token
2. GET  exerp/qr (Authorization: Bearer <user access_token>)               → "exerp:checkin:..."
3. Render that exact string as a QR code on screen.
4. (Optional) Re-fetch on a timer / on screen-on, since the token is time-stamped.
   Cache refresh_token to avoid re-entering the password; refresh via api/email/refresh.
```

No hashing, no secret, no device binding observed in the client. A KaiOS app is
`fetch()` + a JS QR library (e.g. `qrcode-generator` / `qrcode.js`). On a
BlackBerry it's an HTTPS request + any QR widget.

### Open questions to confirm empirically (see PoC)
- **QR validity window:** how long the server accepts a given timestamp/digest.
  Determines how often the dumbphone must re-fetch. (`--probe-validity`)
- **Temp-token lifetime:** how long the client-credentials token stays valid;
  affects whether step 0 must run every login or can be cached.

Resolved during testing:
- Login is two-step; the `access_token` form field must carry the temp token
  (an empty value returns HTTP 400 — this was the first failure).
- `newAuth` uses the `{locale}` path (`es` works).

## 5. Reproduction / tooling used
- Decoded QR: `pyzbar` + Pillow.
- Unpacked XAPK: `unzip`; decompiled DEX with `jadx 1.5.2` (JDK 17).
- Key files in APK:
  - `com/myvitale/api/Api.java` — endpoint list (`getQR`, `newAuth`, `refresh`)
  - `com/myvitale/api/ApiService.java` — OkHttp client, Bearer interceptor, base URL
  - `com/myvitale/api/domain/model/LoginResponse.java` — token model
  - `com/vitale/coredata/data/di/NetworkModule*.java` — `SERVICE_URL`, `appName`
  - `com/vitale/coredata/data/api/interceptor/AuthInterceptor.java` — current Bearer logic
